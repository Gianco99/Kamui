Pass 2 - the interface you will live in
---------------------------------------
The content configs, in config/content/. Start with core.json, then jets.json, tracks.json, leptons.json, then the presets dvLight, dvBase, dvSignal, dvFull, then dvRun2Displaced and dvRun2Lepton. About 500 lines.

This is where your review has the most leverage, because this is the file a physicist edits to add a variable and it is the schema everything else is built around. If it is wrong, the python that consumes it is wrong too.

Specific things to decide rather than just read:

Variable naming. I followed NanoAOD conventions - Jet_pt, Muon_dxy, GenPart_genPartIdxMother - on the theory that people already know them. If you would rather have DVCode names, now is the time, because changing them after a production means reprocessing.

The doc strings on every variable. Every branch has a "doc" field that becomes ROOT branch documentation. Some are useful, some restate the branch name. Prune.

The "_doc" and "_note" comment keys. There are 43 of them across the configs. config/content/core.json has 5, config/samples/run2Validation.json has 7, config/triggers/run2Displaced.json has 6. Some carry real information such as why PV has no maxLen; others are me narrating. Decide which survive.

Precision values. I put 10 to 14 mantissa bits on floats fairly uniformly without deriving it from any resolution requirement. This is the main storage knob and it is currently a guess. Worth setting deliberately, at least for the track and vertex positions where displacement resolution actually matters.


Pass 3 - the code that consumes the configs
-------------------------------------------
kamui/content.py (220 lines), then kamui/catalog.py (186), then kamui/config.py (75). About 480 lines. The package moved to the repo root on 2026-08-25; it used to sit under SamplesFromDAS.

These three are the core. content.py validates a content config and maps physics-facing type names to CMSSW plugins. catalog.py expands sample grids. config.py does JSON loading, comment stripping and include chains.

Known verbosity to attack, with locations:

catalog.py has a 29-line module docstring, 15 percent of the file, which restates the whole schema. Line 7 ends with "which is where DVCode's sample lists went wrong" - that is editorializing and should go.

content.py has a 24-line module docstring. Line 35 reads "is boilerplate the user should never have to type", which is me being pleased with myself rather than informing.

config.py line 4, "Two rules make the JSON files readable without a schema in your head", is the same problem in a smaller file.

The real question underneath all three: is a module docstring the right place for schema documentation at all, or should the schema live once in SamplesFromDAS/CLAUDE.md and the docstrings shrink to one line each? I lean toward the latter but did not do it.

Design choice to decide here: the grid axis format. An axis entry can be a plain string or a dict carrying several substitutions at once, like {"mode": "ggH", "dasMode": "GluGluH-"}. It is the least elegant thing in the repo and it exists because the exotic Higgs dataset names are irregular. If you can see a cleaner encoding, this is the moment.


Pass 4 - the CMSSW boundary
---------------------------
SamplesFromDAS/cmssw/kamuiNtuple_cfg.py (152 lines), SamplesFromDAS/cmssw/kamuiTables.py (126), kamui/slimming.py (128). About 400 lines.

kamuiNtuple_cfg.py is the cmsRun config and is wiring only, no content decisions. kamuiTables.py turns resolved JSON into table producers. slimming.py maps physics-facing group names to EDM outputCommands for the slimmed MiniAOD.

slimming.py lines 9 and 10 explain why groups are named after physics, at length, in a file where it is obvious from the code. Cut.

Design choice: the biggest structural bet in the repo is that the flat tree is built from CMSSW's NanoAOD table producers rather than a hand-written EDAnalyzer. That is why there is no C++ to maintain, and it constrains milestone 4, because the displaced vertexer will have to publish a FlatTable to fit this scheme. If you disagree with that bet, it is much cheaper to say so now than after the vertexer is written.

Design choices to settle
------------------------
Collected in one place so you can decide them without re-reading. My recommendation is given but these are yours.

Output format. Flat ROOT tree as primary, slimmed MiniAOD optional per task. Recommend keeping. The measured cost is real: the slimmed MiniAOD is 49 kB/event against 67.5 for the source, only 1.4 times smaller, because packedPFCandidates alone is 27 kB/event. Keeping tracks means keeping most of MiniAOD. Decide whether the archival copy is worth that.

Table producers versus a custom EDAnalyzer. Recommend keeping, see pass 4.

Run 2 jets. dvRun2Displaced uses CHS slimmedJets because that is what DVCode selected on, while Run 3 presets use PUPPI. I am not confident this is what you want for a like-for-like comparison. Your call.

Run 2 track preselection. DVCode's pixel and strip layer cuts are applied at ntuple time in the Run 2 presets, which bakes a DVCode choice into the stored data. The alternative is storing loose and cutting downstream, at a real storage cost. I applied them; I am not sure that is right.

Trigger path lists per era. DVCode uses one list for all four Run 2 eras with throw=False, so paths outside a year's menu simply never fire, and I replicated that exactly. A per-year list would look more correct and would disagree with DVCode. Recommend keeping the replication for the validation, then revisiting for Run 3.

CMSSW version policy. Settled 2026-08-25 by Gianfranco, so not open: the release is chosen to be recent rather than campaign-matched, currently CMSSW_16_1_2 set in config/sites.json, and is then pinned. It does not get bumped without asking him, because an unpinned framework breaks silently under the people using it. Listed here only so the decision is not relitigated.

Directory naming. Partly settled 2026-08-25: the kamui package moved to the repo root and the CLI to bin/, so SamplesFromDAS is now just the sample-processing stage rather than the whole framework. Still open is whether that name is right for what remains - it holds the content schema, the trigger definitions and the cmsRun config, not only DAS queries.
